# 实测结果

本文件给出当前版本三个变体的设备实测数据。数字取自测量时的原始记录，口径随表说明。每个版本的变化见 [CHANGELOG.md](CHANGELOG.md)。

## 环境

- 设备：Ascend950DT，每卡 64 个 AIV。
- 软件：CANN 9.2.1、bisheng 9.2.1、PyTorch 2.10.0、torch_npu 2.10.0.post7。
- 机器为共享使用，没有独占。同一口径下重复测量的漂移约为 ±2–5 µs（P50），跨轮约 4–5%。
- 上游：保序 QLI V1（`quant_lightning_indexer_ordered`，[`sparse/ops-transformer`，分支 `wzj_qli_order_fused`](https://gitcode.com/sparse/ops-transformer/tree/wzj_qli_order_fused/attention/quant_lightning_indexer_ordered)）；原版基线是 torch_npu 自带的 `npu_quant_lightning_indexer`。
- 所有耗时都是设备侧 kernel 时间（torch_npu profiler 的 `kernel_details.csv`），不含 host 下发、KV 搬运和 attention。

读法：

- 冷重置的耗时随序列长度增长，因为清池要重写整行 `htd`。它只出现在请求刚开始的几步；想把它移出 decode 可以用 `echo_lru_init`。
- `plan_unordered` 的冷重置和热态都明显慢于另外两个，它是回退版本。
- `plan_deferred` 在这张表里按全含口径计时（`ECHO_PATH2_ASYNC=0`，k3 在调用流上）。

## plan：按 MTP 汇总

另一组 144 配置矩阵：GLM-5.2 与构造两种数据 × MTP 0 / 1 / 3 / 7 × batch 8–16 × 序列长度 102,400 / 358,400，容量 = P × 2048，热满池约 90% 命中。下表是每组 18 个配置的均值（µs），plan = k1 + k2 的 kernel-only 时间。

| 数据 | MTP | 0 | 1 | 3 | 7 |
|---|---|---:|---:|---:|---:|
| GLM-5.2 | plan | 48.48 | 43.62 | 72.54 | 167.13 |
| 构造 | plan | 48.83 | 45.38 | 78.13 | 184.13 |

plan 只处理 TopK 索引，耗时基本与序列长度无关（同一 MTP 下两种长度相差不超过约 3 µs），随 batch 从 8 到 16 缓慢增加 5–6 µs。

## plan：与上游 QLI 的衔接

保序 QLI 与 plan 在同一条流上、用同一份输入串行调用，用 profiler 的 kernel 时间戳对账（µs）：

| 用例 | QLI kernel | QLI 结束到 plan k1 开始 | plan k1 | plan k2 |
|---|---:|---:|---:|---:|
| batch 8 / MTP3 / full_cache_75pct | 439.96 | 0.000 | 49.66 | 27.15 |
| batch 4 / MTP7 / full_cache_75pct | 440.30 | 0.000 | 127.26 | 55.40 |
| batch 4 / MTP7 / cold_reset | 438.19 | 0.000 | 32.64 | 152.88 |

两个算子之间没有设备侧空隙。宿主侧每次调用的下发开销（b8 / MTP3 / full_cache_75pct）：

| 项 | 每次调用重新上传 launch 参数 | 本版本 |
|---|---:|---:|
| `echo_lru` host enqueue（带同步循环） | 0.346 ms | 0.017 ms |
| `echo_lru` host enqueue（纯 enqueue） | 0.102 ms | 0.012 ms |
| `echo_lru_init` host | 0.299 ms | 0.016 ms |

本版本把 launch 参数的 device 拷贝按形状缓存，形状不变的稳态下没有 H2D。plan 的宿主开销完全落在 QLI kernel（约 440 µs）之内。

## plan_deferred：边界与全含

六场景的 kernel P50，MTP = 3、rows = 32、20 个样本，取自把簿记拆到 k3 的那一步落地时的读数。边界 = k1 + k2′，是侧流模式下调用流上的规划开销；全含 = k1 + k2′ + k3。

| 场景 | 边界（k1 + k2′） | k3（侧流） | 全含 |
|---|---:|---:|---:|
| cold_reset | 72.60 | 8.3–9.4 | 81.76 |
| warm_75pct | 41.47 | | 49.96 |
| warm_all_hit | 37.21 | | 44.74 |
| full_cache_75pct | 50.53 | | 59.37 |
| full_cache_90pct | 45.83 | | 54.33 |
| full_cache_all_hit | 43.12 | | 50.91 |

与拆分前的 k1 + k2（同机同口径：cold_reset 78.53 / warm_75pct 47.69 / warm_all_hit 41.91 / full_cache_75pct 57.08 / full_cache_90pct 51.81 / full_cache_all_hit 47.54）相比，边界少 4.4–6.6 µs，全含多 2.3–3.4 µs。边界口径的内容与全含不同，不能和 `plan` 的数字直接比较。

## 正确性覆盖

| 变体 | 已验证的范围 |
|---|---|
| plan | 联合测试矩阵全部用例；MTP 0 / 1 / 3 / 7 的六场景 golden（升序输入）；命中率 50% / 75% / 100% × MTP 1、3 × 容量 4096、8192 的 18 组补测 |
| plan_deferred | 联合测试矩阵全部用例；MTP 0 / 1 / 3 的六场景 golden，侧流开关两种状态都通过；上述 18 组命中率补测 |
| plan_unordered | 联合测试矩阵全部用例；MTP 0 / 1 / 2 / 3 的无序 golden（warm_75pct、full_cache_75pct，含满池淘汰）；`torch.npu.graph` 捕获与回放（rows 8 / 32，MTP 0 / 3） |

没有覆盖的部分：`spec_enabled = True` 的投机后缀作废路径不在 golden 范围内；端到端的 host 墙钟时间、KV 搬运和 attention 不在测量范围内。
