# 更新日志

每个版本一条记录，按 what / why / how / results 四段说明。

## V1 — 初始版本：两条路径与无序回退版本

### What

新增 `echo_lru` 目录，包含同一个 KV 缓存规划算子的三个变体：

| 变体 | 定位 |
|---|---|
| `plan` | 当前的主要交付版本 |
| `plan_deferred` | 储备版本：簿记拆到第三个 kernel，为后续掩藏做准备 |
| `plan_unordered` | 回退保证：输入的 TopK 不要求升序 |

另有构建脚本、接口说明、实测结果，以及一套联合测试脚本。

### Why

稀疏注意力配合 KV offload 时，每一步都要把 TopK 选中的 KV 搬上设备。搬运之前必须先知道每个 token 在驻留池里的槽位、哪些 token 缺失、哪些旧槽让位。这个规划结果由每个请求的 LRU 池决定，必须与 KV 的真实驻留位置逐槽一致，而且它处在每一层 decode 的关键路径上。

由此定了三个目标：

1. **正确且确定。** 规划结果逐槽可验证，相同的输入得到相同的结果。
2. **延迟低，能和上游零开销衔接。** 规划与上游 indexer 在同一条流上串行执行时，两者之间没有设备侧空隙，宿主下发被上游 kernel 掩盖。
3. **给后续优化留出结构。** 沿用 Echo 的思路，把管理面做成可以被掩藏的独立阶段。

`plan_unordered` 的存在是因为高性能实现依赖升序输入；上游不能保证升序时需要一条退路。

### How

**plan** 是同一条流上的两个 kernel。k1 负责查找与分类：把一个请求 P 行升序 TopK 合成一份去重 token 表，沿驻留槽的 LRU 顺序扫描并逐槽二分，得到命中槽位，同时产出升序的 miss 清单和 victim / survivor / hit 掩码。k2 负责合并、准入与簿记：按 LRU 顺序淘汰最旧的未命中槽，miss 按 token 升序准入，更新 htd / dth，重建 LRU 顺序。

k1 没有对每个查询去 `htd` 里取槽位，而是沿 LRU 顺序遍历驻留槽、对每个槽在 token 表里二分：工作量正比于驻留槽数，访存是顺序的。工作集放在 UB 里，去重和终结两步用 SIMD 帧实现。

**plan_deferred** 把 k2 拆成 k2′ 和 k3。k2′ 做完本步输出（槽位、miss 清单）就返回；只影响下一步的簿记交给 k3，默认发到侧流。这样调用流上的规划开销只是 k1 + k2′。

**plan_unordered** 保留较早的逐查询查表实现，miss 按首次出现的顺序准入。接口与 `plan` 相同，支持范围更小（P ≤ 4 实测，容量 ≤ 8192）。

实现上的几个要点：

- 三个变体注册同一个 torch 算子名 `sparse_kv_plan_op.echo_lru`，一个进程只加载一个。
- 一个请求的 P 个位置共用一个池；跨位置的重复 token 只准入一次。
- launch 参数由张量形状推导，device 拷贝按形状缓存，稳态下没有 H2D。
- 源码保持测量时的原样，只精简了注释。

### Results

数据与口径见 [RESULTS.md](RESULTS.md)，下面是摘要（Ascend950DT，设备侧 kernel 时间）。

- **正确性。** 联合测试矩阵里三个变体共 144 个候选用例，状态和输出与 CPU 参考逐项一致。
- **plan。** 热满池下 plan 耗时（144 配置均值）：MTP 0 / 1 / 3 / 7 = 48.48 / 43.62 / 72.54 / 167.13 µs（GLM-5.2 数据）。与上游 QLI 串行调用时两算子之间的设备侧空隙为 0 µs，宿主下发 0.017 ms。
- **plan_deferred。** MTP = 3 时调用流上的规划开销（k1 + k2′）为 37.21–50.53 µs（warm_all_hit 至 full_cache_75pct）；k3 的约 8–9 µs 由侧流掩藏。
- **plan_unordered。** MTP3 / 容量 8192 / full_cache_75pct 为 93.0 µs。
